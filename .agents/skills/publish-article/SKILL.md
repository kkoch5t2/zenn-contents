# 記事の公開手順 (publish-article)

ユーザーから「この記事を公開して」と指示された場合は、以下の手順に従って公開作業を行ってください。

## 1. 記事の特定と状態確認
- 対象となる記事（Markdownファイル）を特定します。
- 記事の先頭にあるフロントマターを確認し、`published` が `true` になっていることを確認してください（`false` の場合は `true` に変更します）。

## 2. Gitコミットルールの適用
作業内容（新規公開・更新・削除）に応じて、以下のルールでGitコミットを作成します。コミットメッセージは、エージェントが実行する際の言語のブレを防ぐため**必ず日本語**で記述してください。

### コミットメッセージの構成
コミットメッセージは「1行目（タイトル）」「空行」「3行目以降（詳細な変更内容）」のフォーマットで作成します。

**【1行目: コミットタイトル】**
作業の目的に応じて以下のプレフィックスを使い分け、対象の記事タイトルを記載します。
- 新規公開の場合: `docs(publish): <記事のタイトル>`
- 既存記事の更新の場合: `docs(update): <記事のタイトル>`
- 記事の削除の場合: `docs(delete): <記事のタイトル>`

※ `<記事のタイトル>` はフロントマターの `title` の値をそのまま使用してください。

**【3行目以降: 変更の詳細 (ボディ)】**
何をどのように追加・変更・削除したのか、具体的な変更内容を箇条書きで詳細に記載してください。

**▼コミットメッセージの例 (更新の場合)**
```text
docs(update): Terraformで全て管理して大渋滞。責任分界点を決める重要性を実感した話

- 見出しの絵文字ルールに沿って、小見出しの絵文字を削除
- Terraform運用時のボトルネックに関する具体例を2段落追加
- 結論部分の文章表現をより明確な形に修正
```

- コミットの前に `git status` などを確認し、意図しないファイルが含まれないよう注意します。
- `git add <対象ファイルのパス>` で変更をステージングしてから、上記のフォーマットでコミットを実行してください。
## 3. プッシュと完了報告
- コミットが成功したら、続けて `git push` を実行してリモートリポジトリに変更を反映させます。
- プッシュが完了したことをユーザーに報告します。

## 4. 内部リンクの相互追加（ユーザー確認必須）
- 記事の公開（push）が完了した後、本リポジトリ内の**他の既存記事**の中に、今回公開した記事に関連する内容があれば、そちら側から今回の記事へリンクを貼ることを提案・実行します。
- **注意:** この内部リンク追加によって発生した他の記事の変更については、自動で `git push` は行わず、ユーザーが変更内容（リンクが適切かどうか）を確認してから手動でpushできるよう、ローカルでの変更（またはコミット）に留めてください。
