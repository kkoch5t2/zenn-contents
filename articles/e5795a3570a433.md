インフラのコード化（IaC）を実現するツールとして広く普及しているTerraformですが、システムの成長に伴い、リポジトリの肥大化や実行時間の増大といった運用上の壁にぶつかることが少なくありません。

私も業務でTerraformを使っており、モノレポで運用しているのですが、最近リポジトリが肥大化しており、徐々にplanにかかる時間が長くなっています。

本記事では、Terraformのリポジトリ戦略（モノレポ vs ポリレポ）と、安全かつ小回りの利く運用を実現するための「State分割」の手法について、私の経験を踏まえて書いていきたいと思います。

## モノレポ（Monorepo）とポリレポ（Polyrepo）の違い

Terraformのリポジトリ構成には、大きく分けて2つのアプローチが存在します。
どちらが絶対的に優れているというものではなく、組織規模やチーム体制、権限管理の要件に合わせて適切な構成を選ぶことが重要です。

### モノレポ（Monorepo）

共通モジュールから各環境（dev / stg / prod）の設定まで、すべてのTerraformコードを1つのリポジトリで一元管理する手法です。

#### メリット

- 全体像の把握が容易で、コードの検索やモジュールの再利用がしやすい
- インフラ全体を横断した調査・リファクタリングがしやすい
- ネットワークとアプリケーションなど複数レイヤーにまたがる変更も、1つのPR・コミットで完結できる
- Lintルール（tflint などによる静的チェック）、命名規則、タグ付けルール、CI/CD設定などを1箇所で統一的に管理・強制しやすい

#### デメリット

- 「ネットワークはインフラチームのみ変更可」といったドメイン単位のアクセス制御を行うには、ディレクトリ単位のIAM制御など追加の仕組みが必要
- State分割の設計が甘いと、1つの変更ミスによって影響する範囲が広がりやすい
- 関わる人数・変更量、頻度が増えるほど、同一リポジトリ内でのコンフリクトが起きやすい

### ポリレポ / マルチレポ（Polyrepo）

「ネットワーク基盤」と「データパイプライン」のように、システムが担う役割や管轄するチームごとにリポジトリを物理的に複数へ分割する手法です。

#### メリット

- 「ネットワーク基盤はインフラチームしか変更・マージできない」といった、ドメイン単位での厳密なアクセス制御・権限分離をリポジトリ単位で自然に実現できる
- リポジトリが分かれることでStateも分離されるため、大規模環境でも実行速度を保ちやすい
- 各チームが自分たちのリポジトリを完全に所有でき、他チームとの調整コストが下がる
- 他リポジトリの状況に縛られず、独立してタグ付け・デプロイのサイクルを回せる
- あるリポジトリでの操作ミスが、別リポジトリのStateへ波及しにくい

#### デメリット

- データパイプライン側からネットワーク側の値（VPCのIDなど）を参照する際、`terraform_remote_state`を介した暗黙的な依存関係が生まれ、参照先のoutputが変わった際に気づきにくい形で壊れることがある
- リポジトリ・CIパイプライン・Stateバックエンドの数がそれぞれ増え、管理対象が広がる
- 共通モジュールや規約を全リポジトリへ反映するには、複数リポジトリへの個別対応が必要

### 早見表

| 観点 | モノレポ | ポリレポ |
|---|---|---|
| 全体の見通しやすさ | ◎ 一元的に把握できる | △ 複数リポジトリの横断が必要 |
| 権限・アクセス制御 | △ 追加の仕組みが必要 | ◎ リポジトリ単位で自然に分離 |
| 大規模時の実行速度 | △ State分割の設計次第 | ◎ 物理的に分離されやすい |
| 横断的な変更のしやすさ | ◎ 1つのPRで完結 | △ 複数リポジトリの調整が必要 |
| 導入・運用コスト | ◎ シンプル | △ CI/CDやState管理が複数必要 |
| 向いているフェーズ | 立ち上げ〜中規模組織 | チーム・権限分離が明確な大規模組織 |

とはいえ、後述の通り「実行速度」の課題はモノレポのままでも**State分割**によってかなりの部分を解消できます。
そのため、多くのチームにとっては「まずモノレポ＋State分割で運用し、権限分離が本当に必要になったタイミングでポリレポ化を検討する」のが現実的な進め方だと考えています。

## 構成例：モノレポとポリレポの比較

実際のディレクトリ構成がどのように変わるのか、具体例で比較します。

### パターンA：モノレポ構成例

1つのリポジトリ内に`environments/`と`modules/`が同居し、ディレクトリによって役割を分割する最もオーソドックスな形です。

```bash
# リポジトリ：my-terraform-monorepo
.
├── environments/               # 環境適用のディレクトリ
│   ├── prod/                   # 本番環境
│   │   ├── network/            # ネットワーク層（State分割）
│   │   │   ├── backend.tf      
│   │   │   ├── main.tf         # source = "../../../modules/network" のようにローカルパスで参照
│   │   │   └── variables.tf
│   │   └── data-pipeline/      # データパイプライン層（State分割）
│   └── stg/                    # ステージング環境
│       ├── network/
│       └── data-pipeline/
│
└── modules/                    # 各環境から呼び出す共通モジュール
    ├── network/
    │   ├── main.tf
    │   └── variables.tf
    └── data-pipeline/
```

### パターンB：ポリレポ構成例（ドメイン・役割別）

「ネットワーク基盤」と「データパイプライン」で完全にリポジトリを分けるパターンです。
担当チームが明確に分かれている場合によく採用されます。

```bash
# ==========================================
# リポジトリ1：terraform-network（基盤ネットワーク層）
# ==========================================
.
├── prod/                       # 本番環境
│   ├── backend.tf
│   ├── main.tf                 # VPC、Subnet、セキュリティグループなどの定義
│   └── variables.tf
├── stg/                        # ステージング環境
│   ├── backend.tf
│   ├── main.tf                 # VPC、Subnet、セキュリティグループなどの定義
│   └── variables.tf
└── modules/                    # ネットワーク専用のモジュール
    └── vpc/

# ==========================================
# リポジトリ2：terraform-data-pipeline（データパイプライン層）
# ==========================================
.
├── prod/                       # 本番環境
│   ├── backend.tf
│   ├── main.tf                 # Glue、Step Functionsなどの定義
│   │                           # ※terraform_remote_state等を利用してnetwork層のStateからVPC IDなどを参照する
│   └── variables.tf
├── stg/                        # ステージング環境
│   ├── backend.tf
│   ├── main.tf
│   └── variables.tf
└── modules/                    # データパイプライン専用のモジュール
    └── glue/
```

## 補足：モノレポのままState分割する

モノレポで運用を始め、リソースが増えてくると「Terraformの実行（plan / apply）が遅い」という問題が発生します。
これは、すべてのインフラリソースを1つの巨大な`terraform.tfstate`に詰め込んでしまっている（密結合になっている）ことが原因です。

Terraformは差分を確認する際、現在のクラウドリソースの全状態を確認（Refresh）しにいくため、リソース数が膨大になるとこの確認作業だけで毎回数分〜数十分待たされることになります。
私のプロジェクトでもPlanにかかる時間が徐々に増えております。
これを解決するために「ポリレポにすべきか？」と悩みましたが、簡単に人を増やせるわけでもないので、管理コストが跳ねあがるポリレポ化はできれば避けたい気持ちもありました。

そこで考えたのがモノレポのままでやれる改善策で、とりあえずStateを分割するということです。
Terraformでは **「モノレポのまま、論理的な構成を疎結合にする」**、つまり**変更頻度を軸にディレクトリとStateを物理的に分割する**ことで解決可能です。

ここでは基盤層→データ層→パイプライン層の3層構成を例に、具体的な使い方を見ていきます。

### ディレクトリとbackendをレイヤーごとに分ける

まず、ディレクトリをレイヤーごとに分け、それぞれに個別の`backend.tf`を持たせます。

```bash
# リポジトリ：my-terraform-monorepo
.
└── environments/prod/
    ├── 01-foundation/         # VPC、Subnetなど（滅多に変わらない）
    │   ├── backend.tf
    │   ├── main.tf
    │   └── outputs.tf         # vpc_id、private_subnet_idsを公開
    ├── 02-data/               # RDSなど（たまに変わる）
    │   ├── backend.tf
    │   ├── main.tf            # foundationのoutputsを参照
    │   └── outputs.tf
    └── 03-pipeline/           # Glue、Step Functionsなど（頻繁に変わる）
        ├── backend.tf
        └── main.tf            # foundation・dataのoutputsを参照
```

数字プレフィックス（`01-`、`02-`、`03-`）は、依存関係の順序をディレクトリ名から一目でわかるようにするためのものです。
各`backend.tf`では`key`だけを変え、Stateの保存先をレイヤーごとに分けます。

```hcl
# environments/prod/02-data/backend.tf
terraform {
  backend "s3" {
    bucket         = "my-company-terraform-state"
    key            = "prod/data/terraform.tfstate"
    region         = "ap-northeast-1"
    dynamodb_table = "terraform-lock"
  }
}
```

### terraform_remote_stateで他レイヤーの値を参照する

`01-foundation`のoutputs.tfで`vpc_id`や`private_subnet_ids`を公開しておけば、`02-data`側から次のように参照できます。

```hcl
# environments/prod/02-data/main.tf
data "terraform_remote_state" "foundation" {
  backend = "s3"
  config = {
    bucket = "my-company-terraform-state"
    key    = "prod/foundation/terraform.tfstate"
    region = "ap-northeast-1"
  }
}

resource "aws_db_subnet_group" "main" {
  name       = "main"
  subnet_ids = data.terraform_remote_state.foundation.outputs.private_subnet_ids
}
```

`03-pipeline`でも同様に、`foundation`と`data`両方の`terraform_remote_state`を宣言すれば、両レイヤーの値を組み合わせて利用できます。

### CI/CDは変更されたディレクトリだけplanする

ディレクトリを分けても、CIが毎回全レイヤーをplanしていては速度改善の効果が薄れます。
変更されたパスを見て、該当レイヤーだけ実行するのが基本です。

```yaml
# .github/workflows/terraform-plan.yml（抜粋）
on:
  pull_request:
    paths:
      - 'environments/prod/01-foundation/**'
```

実行コマンド自体も、対象のレイヤーのディレクトリを指定するだけです。

```bash
terraform -chdir=environments/prod/01-foundation plan
```

なお、`terraform_remote_state`は便利ですが、参照が増えるほど依存関係が追いにくくなります。
最初から細かく分けすぎず、まずは基盤／データ／パイプラインの3層程度で始め、特定のレイヤーだけplanが遅くなってきたら、そのレイヤーをさらに分割する、という進め方が現実的です。

## まとめ

Terraformのリポジトリ構成は、まずは管理がシンプルな **「モノレポ」** を採用し、共通化できる設定はモジュールに切り出すのが良いと思います。
ポリレポで管理する場合、どのチームがどのリポジトリをどのようなルールで運用するかなどを考える必要がありルール作りも大変ですし、運用コストもかかるからです。

またモノレポで運用が進みリソースが肥大化してきた際は、慌ててポリレポへ移行するのではなく、 **「変更頻度に応じたStateファイルの分割」** を実施して密結合を解消していくのが良いです。
これにより、日々の実行待ち時間が大幅に短縮され、安全で快適なインフラ運用が実現できます。

さらに組織やチームが拡大し、権限を厳格に分けたいタイミングで初めて、役割別（ネットワークとデータパイプラインなど）のポリレポ化を検討するのがスムーズな移行ステップです。
