データ基盤に携わっていると、Parquetというファイルフォーマットに触れる機会が多いと思います。
S3にデータを置くときも、Athenaでクエリを投げるときも、Sparkでパイプラインを組むときなど、Parquetが登場する場面は多いはずです。

私も実務で利用していますが、「列指向のフォーマットでしょ？」くらいの知識で利用していました。
しかし、実務でParquetを扱う上で **「なぜ列指向だと速くて小さいのか」「内部で何が起きているのか」** を理解しておかないと、パフォーマンスチューニングやトラブルシュート時に手が止まってしまうことがあります。

この記事では、Parquetを「なんとなく使っている」状態から一歩先に進むために、仕組みの部分を体系的に整理しようと思います。

## そもそもParquetとは何か

Apache Parquetは、Hadoopエコシステムから生まれた **列指向（カラムナ）のバイナリファイルフォーマット** です。
2013年にTwitterとClouderaが共同で開発を始め、現在はApache Software Foundationのトップレベルプロジェクトとして広く普及しています。

ポイントは **「ファイルフォーマット」** であるということです。
データベースそのものではなく、**データをどうやってバイト列としてファイルに並べるか** を定義した仕様となっています。
Spark、Athena、BigQuery、Snowflake、Pandas、Polarsなど、多くのツールがParquetの読み書きをサポートしています。

## 行指向と列指向——根本の違いを押さえる

まずは「列指向」の意味を、行指向と対比させて明確にします。

以下のようなユーザーデータをもとに考えていきます。

| id | name | age | dept |
|----|------|-----|------|
| 1  | 田中 | 28  | 営業 |
| 2  | 鈴木 | 35  | 開発 |
| 3  | 佐藤 | 22  | 営業 |

### 📄 行指向（CSV、RDBMSのページなど）

以下のようにデータは **行ごと** にまとめてディスクに書き込まれます。

```
[1, 田中, 28, 営業] → [2, 鈴木, 35, 開発] → [3, 佐藤, 22, 営業]
```

1行のレコードが物理的に近い場所にあるため、「ID=1のレコードを丸ごと取得する」「1行追加する」といった処理は高速です。

### 🏛️ 列指向（Parquet）

以下のようにデータは **列ごと** にまとめてディスクに書き込まれます。

```
id列:   [1, 2, 3]
name列: [田中, 鈴木, 佐藤]
age列:  [28, 35, 22]
dept列: [営業, 開発, 営業]
```

同じ列のデータ（＝同じデータ型の値）が物理的に隣り合って並ぶため、後述する「圧縮」と「読み飛ばし」で圧倒的な威力を発揮します。

## Parquetが広く普及した3つの理由

### 1️⃣ 驚異的な圧縮率：同じ型の値が並ぶから効果的な圧縮が実現

列ごとにデータをまとめると、**同じデータ型、さらには同じ値が連続して並ぶ** 状態になります。
これが圧縮アルゴリズムにとって最高の状態です。

Parquetは汎用の圧縮コーデック（Snappy、GZIP、ZSTDなど）を適用する前に、まずデータの特性に合わせた **エンコーディング** を行います。具体的には以下の3つがあります。

#### 辞書エンコーディング（Dictionary Encoding）

カーディナリティ（値の種類数）が低い列に効果的です。

```
元データ: [営業, 開発, 営業, 人事, 営業, 開発, ...]
辞書: {0: 営業, 1: 開発, 2: 人事}
エンコード後: [0, 1, 0, 2, 0, 1, ...]
```

文字列を整数に置き換えるだけで、データサイズが激減します。
Parquetはデフォルトでこのエンコーディングを試み、カーディナリティが高すぎる場合（1カラムに異なる値が多い場合）は自動的にフォールバックします。

#### ランレングスエンコーディング（Run-Length Encoding / RLE）

同じ値が連続する場合に効果を発揮します。

```
元データ: [営業, 営業, 営業, 営業, 営業, 開発, 開発, ...]
エンコード後: [(営業, 5回), (開発, 2回), ...]
```

ソート済みのデータや、パーティション列のように同じ値が連続しやすい列では、劇的にサイズが縮みます。

#### ビットパッキング（Bit Packing）

整数値の範囲が狭い場合、必要最小限のビット数で表現します。
通常、システム上で数値を扱う際はどんな小さな数でも「32ビット」などの固定枠が使われ、データ内に大量の「無駄な0（空きスペース）」が生じます。
しかしParquetでは、例えばその列に「0〜7（2進数で000〜111）」の値しかないと分かれば、この無駄な0をすべて省き、1値あたり3ビットだけで隙間なく詰め込んで保存します。

以上3つのエンコーディングが効いた上でさらにSnappyやZSTDで圧縮するため、CSVと比較して **数分の一〜十分の一以下** のファイルサイズになることも珍しくありません。

### 2️⃣ 必要な列だけ読む：列プルーニング（Column Pruning）

分析クエリでは、テーブルの全列を使うことはほとんどありません。

```sql
SELECT AVG(age) FROM users;
```

例えば、このクエリに必要なのは `age` 列だけです。

- **CSVの場合：** 行単位で格納されているため、`name` や `dept` のバイト列も含めてすべて読み込み、パース（データを解析してプログラムが扱いやすい形式に変換すること）した上で `age` だけを取り出す必要があります。
- **Parquetの場合：** `age` 列のデータだけがディスク上の特定の位置にまとまっているため、**他の列のバイトを一切読まずにスキップ** できます。

100列あるテーブルから3列だけ使うようなクエリなら、ディスクI/Oが単純計算で約97%削減されます。これが「列指向が分析に強い」と言われる最大の理由です。

:::message
**💡 補足：そもそも「ファイル」に何度もクエリを投げるの？（現代のデータ基盤の常識）**

「データを取り込むためのファイルなら、一度DB（データウェアハウス）に入れてしまえばもう見ないのでは？」と思うかもしれません。
しかし現代のビッグデータ基盤（データレイク等）では、**Parquetファイルそのものがデータベースの実体（ディスク代わり）として直接クエリされ続けます**。

従来の「高価な専用DBに全データをロードして保存する」構成から、「安価なS3にParquetを置き、計算時だけAthenaやBigQueryで直接読みに行く」という構成（コンピュートとストレージの分離）が主流になりました。
そのため、「単なるファイル置き場（S3）」を「高速なDB」のように振る舞わせる必要があり、必要なデータだけを爆速で拾い読みできるParquetの仕組みが絶対不可欠になっているのです。
:::

### 3️⃣ 必要な行グループだけ読む：述語プッシュダウン（Predicate Pushdown）

Parquetファイルには、データ本体だけでなく **統計情報（メタデータ）** が埋め込まれています。
具体的には、各Row Group・各列について以下が記録されています。

- 最小値（min）
- 最大値（max）
- NULL件数（null_count）
- 行数（num_values）

例えば、以下のようなクエリを実行するとします。

```sql
SELECT * FROM users WHERE age >= 40;
```

クエリエンジンはまずParquetのメタデータを読み、あるRow Groupの `age` 列の統計が `min=20, max=35` だと分かれば、**そのRow Groupは条件に該当するデータが絶対にない** と判定できます。結果として、そのRow Groupのデータは解凍すらせずに丸ごとスキップされます。

この仕組みがあるからこそ、S3に置いた数十GBのParquetファイルに対してAthenaでクエリを投げても、秒単位で結果が返ってくるわけです。

## Parquetの内部構造を理解する

Parquetファイルの中身は、3層の階層構造になっています。

```
📦 Parquetファイル（1つの物理ファイル）
├── 🔲 Row Group 1
│   ├── 📊 Column Chunk (id)
│   │   ├── 📄 Page 1
│   │   └── 📄 Page 2
│   ├── 📊 Column Chunk (name)
│   │   └── 📄 Page 1
│   ├── 📊 Column Chunk (age)
│   │   └── 📄 Page 1
│   └── 📊 Column Chunk (dept)
│       └── 📄 Page 1
├── 🔲 Row Group 2
│   └── ...
└── 📋 Footer（メタデータ）
```

### 🔲 Row Group（行グループ）

データを一定の行数ごとに区切った大きな塊です。デフォルトでは128MB程度のサイズで分割されます。
Row Groupが述語プッシュダウンにおけるスキップの単位になるため、**Row Groupのサイズ設計はパフォーマンスに直結** します。

### 📊 Column Chunk（カラムチャンク）

Row Groupの中で、さらに列ごとに分割されたデータの塊です。1つのRow Groupの中の1つの列のデータがすべて含まれます。
列プルーニングでは、不要な列のColumn Chunkをまるごとスキップします。

### 📄 Page（ページ）

Column Chunkの中の最小のI/O単位です。実際のエンコーディングと圧縮はこのPage単位で行われます。
Data Page（実データ）とDictionary Page（辞書データ）の2種類があります。

### 📋 Footer（フッター）

ファイルの **末尾** に配置されるメタデータです。スキーマ定義、各Row GroupやColumn Chunkの位置、統計情報がすべてここに集約されています。

クエリエンジンはまずこのFooterを読み込み、「どのRow Groupのどの列を読む必要があるか」を判断してから、必要なバイト範囲だけをピンポイントで取得します。
S3のようなオブジェクトストレージでは、HTTP Range Requestで必要な部分だけをダウンロードできるため、この構造が非常にうまく機能します。

## ネスト構造のサポート：Dremelの仕組み

Parquetの特徴的な機能の一つが、**ネストされた複雑なデータ構造** を扱える点です。
JSONのような入れ子構造を列指向で表現するのは一見難しそうですが、ParquetはGoogleの論文「Dremel」で提案された手法を採用しています。

具体的には、ネストされたフィールドごとに **Repetition Level（繰り返しレベル）** と **Definition Level（定義レベル）** という2つの整数値を付与し、これによってネストの深さやNULLの位置を正確に復元できるようにしています。

```json
{
  "name": "田中",
  "addresses": [
    {"city": "東京", "zip": "100-0001"},
    {"city": "大阪", "zip": "530-0001"}
  ]
}
```

このようなデータでも、`addresses.city` や `addresses.zip` をそれぞれ独立した列として格納し、列指向の恩恵（圧縮・列プルーニング）をフルに受けられます。
BigQueryがネストしたSTRUCT（構造体）やARRAY（配列）を高速に処理できるのは、まさにこの仕組みのおかげです。

## 実務で押さえておくべきポイント

### ✅ Parquetが向いているケース（OLAP・分析用途）

- **データレイク（S3、GCSなど）への保存:** 圧縮率が高いためストレージコストが削減され、列プルーニングのおかげでクエリのスキャン量も最小限に抑えられます。AWSならAthena、GCPならBigQueryのストレージとして定番です。
- **ETL/ELTパイプラインの中間データ:** Sparkなどの分散処理エンジンで中間結果を一時的にS3へ書き出す際、Parquetを使うとI/O待ちが大幅に減ります。
- **機械学習の学習データ:** 特徴量の一部だけを読み込みたい場面が多いため、列プルーニングの恩恵が大きいです。

### ❌ Parquetが向いていないケース（OLTP・トランザクション処理）

- **1行単位のINSERT/UPDATE/DELETE:** 列ごとにデータが分かれているため、1行を更新するには複数のColumn Chunkを書き換える必要があります。さらにParquetはイミュータブル（不変）なファイルフォーマットなので、原則としてファイル全体を書き直すことになります。（あとから一部だけを書き換えることができない）
- **リアルタイムな追記:** ストリーミングで1件ずつデータが到着するような場面では、Parquetファイルを都度生成するのは非効率です。一般的には、一定量をバッファリングしてからまとめてParquetに変換します。

### ⚙️ パフォーマンスに影響する設計上の重要ポイント

| 項目 | 指針 |
|------|------|
| **Row Groupサイズ** | 大きすぎるとメモリを圧迫し、小さすぎると統計情報によるスキップの粒度が粗くなる。128MB〜256MBが一般的な目安。 |
| **圧縮コーデック** | 速度重視ならSnappy、圧縮率重視ならZSTD。GZIPは互換性は高いがSnappyやZSTDと比べると中途半端な立ち位置。 |
| **ソート順** | WHERE句でよく使うカラムでソートしておくと、統計情報（min/max）の効きが劇的に良くなる。述語プッシュダウンでスキップされるRow Groupが増える。 |
| **パーティショニング** | 日付やカテゴリなど、フィルタ条件に使われる列でディレクトリ分割（Hive-style partitioning）すると、ファイル単位で読み飛ばせる。 |

## まとめ

Parquetの強さは、単に「列ごとに保存している」というだけではなく、以下の仕組みが組み合わさって実現されています。

1. **エンコーディング（辞書、RLE、ビットパッキング）＋圧縮コーデック** でデータサイズを極限まで縮める
2. **列プルーニング** で不要な列のI/Oを完全にスキップする
3. **統計情報による述語プッシュダウン** で不要な行グループのI/Oもスキップする
4. **Footer（メタデータ）をファイル末尾に集約** し、まず目次を読んでから必要な部分だけを取りに行く

この構造を理解しておくと、「なぜソートしておくとクエリが速くなるのか」「なぜRow Groupサイズの設計が重要なのか」「なぜParquetで1行更新が苦手なのか」といった疑問にすべて筋道立てて答えられるようになります。
